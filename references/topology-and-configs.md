# Topology, `topology.yaml`, configs, deltas and markers

## 1. Design rules

- **Every concept must be exercisable**:
  - DR/BDR election, flooding or FHRP needs a multi-access segment.
  - Path selection or feasible successors need redundant paths of *unequal* cost; use an interface metric knob in the baseline, e.g. `extra: ["delay 300"]`.
  - Inter-domain features need a separate domain.
  - Filtering and summarization need several prefixes, so use loopbacks.
  - End-to-end symptoms need a host.
  - NBMA or hub-and-spoke behaviour can be emulated on a shared segment with unicast/static neighbors.
- **Smallest topology that does the job.** Ask for the node budget if you need more than about 8 nodes. Use loopbacks to simulate LANs.
- **Names:** R1..Rn, D1/D2 (L3 switches), A1.. (access), PC1../H1.., SRV1, SW1 (unmanaged), ISP/INET.
- **Decodable addressing:**
  - link Rx-Ry: `10.<site>.xy.0/24`
  - loopbacks and router IDs: `x.x.x.x`
  - IPv6: `2001:db8:acad:xy::/64`, link-local `fe80::x`
  - external networks: RFC 5737 / `2001:db8::/32` only
  - private AS numbers, unless the book uses specific ones
- **Draw zones** (areas, AS, VRFs, sites, hub-and-spoke) so the diagram carries the logical design.

## 2. `LAB/topology/topology.yaml` (source of truth)

```yaml
lab:
  title: "Course ChN - Topic - Suffix"     # CML maximum: 64 characters
  short_title: "ChN - Topic"               # used for ticket lab titles (+ " - Ticket N")
  description: "..."                       # CML lab description (max 4096)
  notes: |                                  # CML lab notes (max 32768): how to start, what is missing
    ...
  platform: cisco-ios                      # default profile for routers/switches (assets/platforms/*.yaml)
  host_platform: linux-host                # default profile for hosts/servers
  included: "hostname, console, addressing, ..."      # baseline header text
  not_included: "the chapter features the learner configures"
  checkpoints: [2, 4]                      # Parts that get solutions/checkpoints/part-N (default: all but last)

nodes:
  - name: R1
    role: router            # router | l3switch | switch | host | server | firewall | cloud | hub | wan
    image: {cml: iol-xe, gns3: "IOU L3"}   # per-emulator definition/template
    platform: cisco-ios     # optional override of lab.platform
    x: -320                 # canvas coordinates; y grows downwards; keep about 200 px spacing
    y: 120
    caption: ["HQ edge"]    # extra lines under the node in the SVG
    show_loopbacks: true
    extra: ["ip cef"]       # extra global lines in the baseline
    config: ../initial-configs/R1.cfg   # ONLY for a hand-written baseline (otherwise generated)
    interfaces:
      - name: Ethernet0/0   # exact name on the image
        ipv4: 10.1.1.1/24   # string or list (2nd+ = secondary)
        ipv6: [2001:db8:acad:1::1/64, "fe80::1 link-local"]
        description: "LAN1"
        extra: ["delay 300"]          # extra interface lines in the baseline
        configured_in_lab: false      # true = the learner adds this address (validate stays quiet)
        slot: 0                       # emulator slot override when the name pattern is unknown
  - name: PC1
    role: host
    image: {cml: alpine}
    gateway: 10.1.1.1       # hosts: default route
    interfaces: [{name: eth0, ipv4: 10.1.1.10/24}]
  - name: SW1
    role: hub               # unmanaged switch: no config generated
    image: {cml: unmanaged_switch}
    interfaces: [{name: port0}, {name: port1}]

links:
  - [R1:Ethernet0/0, PC1:eth0]
  - {a: R1:Ethernet0/2, b: R3:Ethernet0/2, style: dashed, label: "10.1.13.0/24\nbackup"}

zones:
  - {name: "EIGRP AS 100", nodes: [R1, R2, R3], color: "#2563eb", padding: 95}
```

Unused interfaces should still be listed. The profile then emits its "unused" lines; IOL needs IP configuration on every interface, or it hangs in the setup dialog.

## 3. Generated vs. written files

| You write | `labkit.py build` generates |
|---|---|
| `topology/topology.yaml` | `initial-configs/<dev>.cfg|.sh` (with the "generated by labkit" mark; hand-written files without the mark are left alone) |
| `solutions/deltas/<dev>.part<N>.cfg` | `solutions/final-configs/`, `solutions/checkpoints/part-<N>/` |
| `solutions/tickets/ticket-<N>/<dev>.delta`, `solutions/tickets/challenge/<dev>.delta` | `troubleshooting/ticket-<N>/<dev>.cfg` (final + fault, with no marker comment), `topology/ticket-<N>.cml.yaml` |
| `lab-guide.md`, `solutions/answer-key.md` (with markers) | marker regions filled, `topology/topology.svg`, `topology/addressing-table.md`, `topology/cml-lab.yaml`, `_work/cml-lab.json` |

**Delta rules:**

- Use the device's CLI syntax, and make the delta pasteable in configuration mode: close every context with `exit`.
- Each delta holds only what that Part adds. If a Part *removes* something, use `no ...` lines.
- A ticket delta is appended to the final config. Later lines override earlier ones: a re-entered `key-string` or `eigrp stub receive-only`, for example, replaces the earlier setting.
- Commands that need interactive confirmation belong in the guide or answer key, not in deltas.

**Platform profiles** (`assets/platforms/<name>.yaml`, or `LAB/topology/platforms/<name>.yaml` to override per lab) hold:

- the comment character and file extension
- the base lines, with `{name}` substituted
- the interface stanza templates: open, description, IPv4, IPv6, up, unused, close
- `gateway_v4` for hosts
- the separator and footer

To add a vendor (Junos, EOS, FRR, VyOS ...), copy a profile and change the templates; no code is needed. Platforms whose config is hierarchical (Junos set-style) work if every line is self-contained.

## 4. Markdown markers (expanded in place by build and by md2pdf)

The marker line stays in the file; the generated content follows it, ending with `<!-- @end -->`. Re-running replaces the region. Never edit inside a region: change the source, then rebuild.

```
<!-- @objectives -->                 <!-- @table addressing -->
<!-- @include skill:snippets/how-to-use.md -->   (or a path relative to the lab root)
<!-- @deltas part=2 -->              <!-- @ticket 1 -->   <!-- @ticket challenge -->
<!-- @code solutions/final-configs/R1.cfg text -->
```

Snippets shipped in `assets/snippets/`: `readiness-intro`, `how-to-use`, `ticket-method`, `ticket-worksheet`, `command-reference`, `hint-intro`, `answer-key-intro`.

## 5. Lint exemptions

`lint` flags any solution line (from `solutions/`, minus the baseline) that appears in the guide. Put `<!-- leak-ok -->` on the line before a code block that legitimately shows commands, such as the Part 1 setup.
